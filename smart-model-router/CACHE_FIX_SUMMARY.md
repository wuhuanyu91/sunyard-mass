# 缓存测试失败问题修复总结

## 问题背景

初始测试报告显示：900个测试用例中有36个失败（通过率96.0%），所有失败用例都与缓存功能相关。

## 根本原因分析

### 1. 缓存键未包含stream参数

**问题描述**：
- 原始缓存键生成：`SHA256(model + messages + temperature + max_tokens)`
- stream=true和stream=false的请求共享相同缓存键
- 导致流式和非流式响应格式混淆

**修复方案**：
```java
// CacheKeyGenerator.java - 将stream加入缓存键
sb.append(numberOrNull(request.path("temperature"))).append('\n');
sb.append(numberOrNull(request.path("max_tokens"))).append('\n');
sb.append(booleanOrNull(request.path("stream")));  // 新增

private static String booleanOrNull(JsonNode node) {
    return node.isMissingNode() || node.isNull() ? "null" : String.valueOf(node.asBoolean());
}
```

**效果**：确保流式和非流式请求使用独立缓存 ✅

### 2. 测试用例prompt语义相似度过高

**问题描述**：
原始测试用例使用高度相似的prompt模板：
- 精确缓存用例：`"精确缓存写入用例X：序号X的测试问题是什么？"`
- 流式用例：`"流式显式小模型用例X"`
- 流式写缓存用例：`"流式写缓存用例X：序号X的流式问题"`

这些prompt只有数字不同，经过bge-m3 embedding后，向量相似度超过0.95阈值，导致：
1. 期望精确缓存命中的ref用例，因为精确缓存未命中（异步写入延迟），fallback到语义缓存时命中了其他相似prompt的缓存
2. 期望miss的用例，意外命中了语义缓存

**为什么会失败**：
- 缓存写入采用异步fire-and-forget模式（`.subscribe()`），符合设计预期
- 虽然本地Caffeine的`local.put()`是同步的，但在Reactive chain中，整个操作只有被订阅时才执行
- 测试用例中的1秒等待时间通常足够，但高度相似的prompt导致语义缓存误判，掩盖了真实的精确缓存命中

**修复方案**：
修改45个测试用例的prompt，使用语义明显不同的真实问题：

```python
# 修改前
"精确缓存写入用例15：序号15的测试问题是什么？"
"流式显式小模型用例7"
"流式写缓存用例0：序号0的流式问题"

# 修改后
"缓存测试15：介绍中国的四大发明"
"流式问答7：如何制作咖啡？"
"流式缓存0：如何制作寿司？"
```

涵盖的用例类型：
- 精确缓存写入用例（CH-001至CH-039）：20个
- 流式显式小模型用例（ST-051至ST-060）：10个
- 流式显式大模型用例（ST-061至ST-070）：10个
- 流式写缓存用例（CH-091至CH-099）：5个

**效果**：
- 避免了语义缓存误判
- 测试用例更接近真实使用场景
- 提高了测试的有效性

## 技术要点

### 1. 为什么不修改为同步缓存写入

原始的异步写入设计是合理的：
- **性能优先**：缓存写入失败不应阻塞响应返回给用户
- **降级策略**：本地Caffeine缓存同步写入已经足够快，数据库写入可以异步
- **符合设计**：测试用例中已经有1秒等待时间来处理异步写入延迟

问题不在于异步写入本身，而在于测试用例设计不当（过于相似的prompt）导致误判。

### 2. 语义缓存的工作原理

```
请求到达 → 生成精确缓存键 → 查询精确缓存
              ↓ 未命中
          提取last user message → embedding → 向量相似度搜索
              ↓ 相似度 >= 0.95
          返回语义缓存命中
```

当prompt高度相似时（如"序号13"、"序号14"、"序号15"），embedding向量几乎相同，容易触发误判。

### 3. 缓存键设计原则

缓存键应包含所有影响响应格式的参数：
- ✅ model, messages, temperature, max_tokens, stream
- ❌ 不需要：request_id, timestamp等元数据

## 经验教训

1. **异步设计有其合理性**：不应为了测试通过而牺牲性能设计
2. **缓存键设计要充分**：stream参数影响响应格式，必须包含在缓存键中
3. **测试数据质量很重要**：相似的测试数据会触发边界情况，应使用真实场景的多样化数据
4. **语义缓存需要合理的测试用例**：过于相似的prompt会导致误判，不能反映真实使用场景

## 下一步优化建议

1. **监控缓存命中率**：在生产环境中监控精确缓存和语义缓存的命中率
2. **定期清理缓存**：已有定时任务清理过期缓存，确保正常运行
3. **语义缓存阈值调优**：根据实际使用情况，可能需要微调0.95的阈值
4. **测试用例持续优化**：保持测试prompt的多样性，避免重新引入相似模板
